# Domain 5: Context Management & Reliability — 15%

This is the smallest domain by weight, but it is where reliability engineering lives, and the wrong answers here are almost always the plausible-sounding shortcut — average the conflicting numbers, escalate on an angry tone, trust the 97% aggregate. For each Task Statement below, read *What's tested*, run the *Self-audit* honestly, then paste the *Deep-dive prompt* into an LLM to have it teach the concept, produce concrete examples and counter-examples, and quiz you until you can answer the *Active-recall self-check* from memory. The unifying skill is preserving fidelity — of facts, of provenance, of error signal, of accuracy measurement — against everything (summarization, position effects, aggregation, averaging) that quietly destroys it.

## Task Statement 5.1 — Manage conversation context to preserve critical information across long interactions

### What's tested
**Knowledge of:** progressive-summarization risk — condensing numerical values, percentages, dates, and customer-stated expectations into vague summaries; the "lost in the middle" effect, where models reliably process the beginning and end of long inputs but may omit findings from the middle; how tool results accumulate in context and consume tokens disproportionately to their relevance (40+ fields per order lookup when only 5 matter); the importance of passing complete conversation history in subsequent API requests to maintain coherence.
**Skills in:** extracting transactional facts (amounts, dates, order numbers, statuses) into a persistent "case facts" block included in each prompt, outside the summarized history; persisting structured issue data into a separate context layer for multi-issue sessions; trimming verbose tool outputs to only the relevant fields before they accumulate; placing key-findings summaries at the beginning of aggregated inputs and using explicit section headers to mitigate position effects; requiring subagents to include metadata (dates, source locations, methodological context) in structured outputs; modifying upstream agents to return structured data (key facts, citations, relevance scores) instead of verbose content and reasoning chains when downstream agents have limited context budgets.
*Self-audit:* You can explain why the "case facts" block lives outside the summarized history, and name the position where key findings must go and the one to avoid.

### Distilled notes
Two forces destroy critical information in a long conversation, and their fixes are different. First, **progressive summarization** compresses the transcript to save tokens, and compression is lossy exactly where you can't afford it — a summary turns "$347.82 refunded on 2026-03-14 for order #A-91" into "a refund was processed." The fix is a separate **"case facts" block**: transactional facts (amounts, dates, order IDs, statuses, customer-stated expectations) live in their own persistent layer that is injected verbatim into every prompt and is *never* fed through the summarizer. The summary keeps the conversation coherent; the facts block keeps the numbers exact. The same move applies to a multi-issue session — each issue's structured data goes into its own context layer.

Second, position. The **"lost in the middle"** effect means the model reliably attends to the beginning (primacy) and the end (recency) of a long input but may silently omit content buried in the middle. So put key findings at the **start**, optionally restate them at the **end**, and give the detailed body **explicit section headers** so the model can navigate rather than skim. Never place something critical in the middle of a long input and assume it will be used.

Third, the token economy of tool outputs. An order lookup that returns 40+ fields when 5 are relevant doesn't just waste budget — the noise crowds out signal as it accumulates. Trim verbose tool output to the relevant fields **at the moment you receive it**, before it piles up in context. Upstream in a multi-agent system the same principle says an upstream agent should return a **structured extract** (key facts, citations, relevance scores) rather than raw content and reasoning chains, especially when the downstream agent has a small context budget.

One thing you do *not* trim: the conversation history sent to the API. Coherence across turns depends on passing the complete history each request; the economy comes from a persistent facts layer and trimmed tool outputs, not from dropping turns.

### Deep-dive prompt
> I'm studying context preservation in long agent conversations. (1) Explain progressive-summarization risk and design a "case facts" block: what goes in it, why it sits outside the summarized history, and how it's injected each turn. (2) Explain the "lost in the middle" effect and the primacy/recency-plus-section-headers layout that mitigates it. (3) Explain why verbose tool outputs (40+ fields when 5 matter) should be trimmed on receipt, and how an upstream agent should return structured extracts for a context-limited downstream agent. (4) Now quiz me: give me five short scenarios one at a time and ask "what gets persisted, trimmed, or repositioned?", then critique my answers.

### Active-recall self-check
1. Why does a "case facts" block live outside the summarized history, and what exactly belongs in it?
2. Where in a long input do you place key findings and where do you never place them, and what is the effect called?
3. An order lookup returns 40+ fields but only 5 are relevant — when and how do you trim it, and why not later?

## Task Statement 5.2 — Design effective escalation and ambiguity resolution patterns

### What's tested
**Knowledge of:** appropriate escalation triggers — a customer's explicit request for a human, policy exceptions/gaps (not merely "complex" cases), and the inability to make meaningful progress; the distinction between escalating immediately when a customer explicitly demands it versus offering to resolve when the issue is straightforward; why sentiment-based escalation and self-reported confidence scores are unreliable proxies for actual case complexity; how multiple customer matches require clarification (requesting an additional identifier) rather than heuristic selection.
**Skills in:** adding explicit escalation criteria with few-shot examples to the system prompt demonstrating when to escalate versus resolve; honoring explicit human-agent requests immediately without first investigating; acknowledging frustration while offering resolution when the issue is within capability, escalating only if the customer reiterates; escalating when policy is ambiguous or silent on the specific request (e.g. competitor price-matching when policy only addresses own-site adjustments); asking for additional identifiers on multiple tool-result matches instead of selecting by a heuristic.
*Self-audit:* You can list the valid escalation triggers, name the two unreliable proxies, and explain why an ambiguous match calls for a question rather than a heuristic.

### Distilled notes
Escalation is a *routing decision*, and this statement rewards routing on the right signal. **Valid triggers:** the customer explicitly asks for a human; policy is silent or ambiguous on their specific request (a genuine policy gap, not just a hard case); the agent lacks the authority or permissions to act; or the agent cannot make meaningful progress. **Unreliable proxies (not triggers):** negative sentiment and self-reported confidence. Both fail for the same reason — they don't correlate with whether the case is *solvable*. Sentiment measures emotion, not complexity: an angry customer can have a trivial, in-scope request. Self-reported confidence is poorly calibrated — the model is often most confident exactly where it is wrong — so a bare confidence score is not a gate.

That gives two sharp behaviors. When a customer is **frustrated but the request is simple and in scope**, don't escalate on tone: acknowledge the frustration and offer to resolve it now; escalate only if they *reiterate* that they want a human. When a customer **explicitly demands a human**, honor it immediately — don't run an investigation first. The distinction is between an explicit demand (act now) and a mere signal of difficulty (offer to resolve).

**Ambiguity resolution** is the sibling skill. When a lookup returns **multiple matches** (two customers with the same name), the correct move is to **request an additional identifier** — not to pick one by a heuristic like "most recent" or "first result." Guessing silently trades a known ambiguity for a hidden error. And because escalation criteria are fuzzy judgment calls, you encode them in the **prompt with few-shot examples** that contrast escalate-vs-resolve cases, not in a hook — this is the determinism-vs-calibration split from Domain 1 applied to a probabilistic decision.

### Deep-dive prompt
> I'm studying escalation and ambiguity resolution for a support agent. (1) List the valid escalation triggers and explain why negative sentiment and self-reported confidence are unreliable proxies for case complexity. (2) Contrast the correct response to a frustrated-but-simple request versus an explicit demand for a human. (3) Explain why multiple customer matches call for asking for another identifier rather than a heuristic pick, and why escalation criteria belong in the prompt with few-shot examples rather than in a hook. (4) Quiz me: give me six short scenarios one at a time and ask "escalate now, offer to resolve, or ask for clarification?", then critique my reasoning.

### Active-recall self-check
1. Name the valid escalation triggers, and the two proxies that are *not* triggers — why do both fail?
2. A customer is clearly angry but the request is simple and in scope. What do you do, and when do you finally escalate?
3. A lookup returns two customers with the same name. What is the correct action, and what is the failure mode of choosing heuristically?

## Task Statement 5.3 — Implement error propagation strategies across multi-agent systems

### What's tested
**Knowledge of:** structured error context (failure type, attempted query, partial results, alternative approaches) as what enables intelligent coordinator recovery decisions; the distinction between access failures (timeouts needing a retry decision) and valid empty results (successful queries with no matches); why generic error statuses ("search unavailable") hide valuable context from the coordinator; why silently suppressing errors (returning empty results as success) and terminating entire workflows on a single failure are both anti-patterns.
**Skills in:** returning structured error context — failure type, what was attempted, partial results, and potential alternatives — so the coordinator can recover; distinguishing access failures from valid empty results in error reporting; having subagents implement local recovery for transient failures and propagate only errors they cannot resolve, including what was attempted and partial results; structuring synthesis output with coverage annotations indicating which findings are well-supported versus which topic areas have gaps due to unavailable sources.
*Self-audit:* You can list the fields a subagent should return on failure, and explain why "access failure" and "valid empty result" must be distinguishable.

### Distilled notes
When a subagent fails, *what it returns to the coordinator* determines whether the system can recover. Return **structured error context**, not a status string: the **failure type**, the **query or action attempted**, any **partial results** already gathered, **alternative approaches** worth trying, and a **retryable** flag. With that, the coordinator can make an intelligent decision — retry, try an alternate source, proceed with partials, or escalate. With a generic `"search unavailable"` it can do none of those, because the real cause is hidden.

The critical distinction is **access failure versus valid empty result**. A timeout is an access failure and may warrant a retry; a successful query that legitimately returned no matches is a valid empty result and must *not* be retried. Collapsing the two is the trap: reporting empty-as-success erases a real failure (the coordinator thinks it has the answer when the search never ran), and treating a valid-empty as an error triggers pointless retries.

Two anti-patterns bracket the correct behavior. **Silently suppressing errors** (returning empty as success) destroys the signal the coordinator needs. **Terminating the whole workflow on one subagent's failure** throws away every other subagent's partial results and the chance to recover. The correct middle is **local recovery plus selective propagation**: the subagent handles what it can locally — retry with backoff for transient faults, reformulate its own malformed query — and propagates upward only the **unresolvable** failure, together with what it attempted and any partial results. Finally, when synthesis must proceed over incomplete inputs, mark it: **coverage annotations** state which findings are well-supported and which topic areas have gaps because a source was unavailable — graceful degradation with transparency, so the coordinator knows the shape of what's missing rather than seeing false completeness.

### Deep-dive prompt
> I'm studying error propagation in multi-agent systems. (1) Design the structured error object a subagent returns on failure — list every field and what the coordinator does with each. (2) Explain the difference between an access failure and a valid empty result, and what breaks if a subagent conflates them. (3) Explain the two anti-patterns (silently suppressing errors; terminating the whole workflow on one failure) and the local-recovery-plus-selective-propagation pattern that replaces them, including coverage annotations in synthesis. (4) Quiz me: give me five short failure scenarios one at a time and ask "recover locally, propagate, or fail the workflow — and what do you return?", then critique my answers.

### Active-recall self-check
1. What fields belong in the structured error context a subagent returns, and what decision does each enable for the coordinator?
2. Why must an access failure and a valid empty result be reported differently, and what goes wrong if they're merged?
3. A subagent hits a transient timeout. What should it do itself, and what — if anything — should it propagate upward?

## Task Statement 5.4 — Manage context effectively in large codebase exploration

### What's tested
**Knowledge of:** context degradation in extended sessions — the model starts giving inconsistent answers and referencing "typical patterns" rather than the specific classes it discovered earlier; the role of scratchpad files for persisting key findings across context boundaries; subagent delegation for isolating verbose exploration output while the main agent coordinates high-level understanding; structured state persistence for crash recovery — each agent exports state to a known location, and the coordinator loads a manifest on resume.
**Skills in:** spawning subagents to investigate specific questions ("find all test files," "trace the refund-flow dependencies") while the main agent preserves high-level coordination; maintaining scratchpad files of key findings and referencing them for subsequent questions to counteract degradation; summarizing key findings from one exploration phase before spawning subagents for the next, injecting summaries into initial context; designing crash recovery with structured agent-state exports (manifests) that the coordinator loads on resume and injects into agent prompts; using `/compact` to reduce context usage during extended exploration when context fills with verbose discovery output.
*Self-audit:* You can name the tell-tale symptom of context degradation and three mechanisms that counteract it.

### Distilled notes
Long exploration sessions **degrade**, and the symptom is specific: the model starts giving inconsistent answers and hedging with "typical patterns" or "usually you'd see…" instead of naming the actual classes and files it found earlier. That is the signal that discovered facts have fallen out of usable context — it is the same information-loss problem as 5.1, now over a codebase instead of a support case.

Four mechanisms counteract it, and they compose. (1) **Scratchpad files** — the agent writes key findings to a file and re-reads them for later questions, so findings persist across context boundaries instead of decaying inside the window. (2) **Subagent delegation** — spawn a subagent to answer a narrow question ("find all test files," "trace the refund-flow dependencies") so the verbose discovery output stays in the subagent's context and only a summary returns to the main agent, which keeps the high-level map. This is Domain 1's context-isolation benefit applied to exploration. (3) **Phase summarization** — before moving from one exploration phase to the next, summarize the phase's findings and inject that summary into the next phase's initial context, so each phase starts clean but informed. (4) **`/compact`** — reduce context usage in place when the window fills with verbose output.

For reliability across crashes, add **structured state persistence**: each agent **exports its state to a known location**, and the coordinator **loads a manifest on resume** and injects it back into the agent prompts. Recovery is deterministic because state lives in files with a manifest, not only in a volatile session. The through-line for this whole statement: **externalize findings to durable storage** (files, summaries, manifests) and **isolate verbosity in subagents** so the main agent's context stays small, current, and specific.

### Deep-dive prompt
> I'm studying context management for large-codebase exploration with Claude Code. (1) Describe the symptom of context degradation in a long session and why "referencing typical patterns instead of the specific classes found earlier" is the tell. (2) Explain four counter-measures — scratchpad files, subagent delegation for verbose sub-questions, phase summarization injected into the next phase, and `/compact` — and when each applies. (3) Design crash recovery using per-agent state exports and a coordinator manifest loaded on resume. (4) Quiz me: give me five short exploration situations one at a time and ask "which mechanism do you reach for?", then critique my answers.

### Active-recall self-check
1. What is the tell-tale symptom that a long exploration session has degraded, and what does it indicate about context?
2. Why delegate a verbose sub-question ("trace all dependencies of the refund flow") to a subagent rather than running it in the main session?
3. How do you design crash recovery so a coordinator can resume exploration after a crash?

## Task Statement 5.5 — Design human review workflows and confidence calibration

### What's tested
**Knowledge of:** the risk that aggregate accuracy metrics (e.g. 97% overall) may mask poor performance on specific document types or fields; stratified random sampling for measuring error rates in high-confidence extractions and detecting novel error patterns; field-level confidence scores calibrated using labeled validation sets for routing review attention; the importance of validating accuracy by document type and field segment before automating high-confidence extractions.
**Skills in:** implementing stratified random sampling of high-confidence extractions for ongoing error-rate measurement and novel-pattern detection; analyzing accuracy by document type and field to verify consistent performance across all segments before reducing human review; having models output field-level confidence scores, then calibrating review thresholds using labeled validation sets; routing extractions with low model confidence or ambiguous/contradictory source documents to human review to prioritize limited reviewer capacity.
*Self-audit:* You can explain why a high aggregate-accuracy number is not sufficient to automate, and what measurement replaces it.

### Distilled notes
The headline failure is that **an aggregate accuracy number hides segment-level failure**. "97% overall" can conceal 60% accuracy on one document type or one field — averaged across a large, easy majority, a catastrophic minority disappears. So a high aggregate is *not* a license to automate. Before you reduce human review, you must **measure accuracy by segment — per document type and per field** — and confirm performance is consistent across *all* of them, not just in aggregate.

The measurement tool is **stratified random sampling**: sample within each stratum (document type, field) rather than uniformly, so rare-but-important segments are actually represented, and keep sampling **on an ongoing basis** to catch **novel error patterns** as inputs drift. To direct scarce reviewer attention, have the model emit **field-level confidence scores**, then **calibrate the review threshold on a labeled validation set** — raw model confidence is not trustworthy until it is checked against ground truth. Route to a human the extractions with **low calibrated confidence** or with **ambiguous or contradictory source documents**, and let the well-supported high-confidence ones through. That is how you spend limited review capacity where errors actually concentrate instead of spreading it uniformly.

Note the link to 5.2: self-reported confidence is only trustworthy *after* calibration against labels. Uncalibrated model confidence is an unreliable proxy in both statements — a routing threshold, like an escalation trigger, must rest on a signal that correlates with real outcomes.

### Deep-dive prompt
> I'm studying human-review workflows and confidence calibration for an extraction pipeline. (1) Explain why a 97% aggregate accuracy can be dangerous and what segment-level measurement replaces it. (2) Explain stratified random sampling — why stratify by document type and field, and why sample on an ongoing basis. (3) Explain field-level confidence scores, calibrating the review threshold on a labeled validation set, and which extractions to route to humans. (4) Quiz me: give me five short pipeline decisions one at a time and ask "safe to automate, or route to review — and how would you measure it?", then critique my answers.

### Active-recall self-check
1. Why is "97% overall accuracy" not enough to automate high-confidence extractions, and what do you measure instead?
2. What is stratified random sampling here, and why stratify by document type and field rather than sampling uniformly?
3. How do you turn raw model confidence into a usable review-routing threshold, and which extractions go to a human?

## Task Statement 5.6 — Preserve information provenance and handle uncertainty in multi-source synthesis

### What's tested
**Knowledge of:** how source attribution is lost during summarization when findings are compressed without preserving claim-source mappings; the importance of structured claim-source mappings that the synthesis agent must preserve and merge when combining findings; how to handle conflicting statistics from credible sources — annotating conflicts with source attribution rather than arbitrarily selecting one value; temporal data — requiring publication/collection dates in structured outputs to prevent temporal differences from being misread as contradictions.
**Skills in:** requiring subagents to output structured claim-source mappings (source URLs, document names, relevant excerpts) that downstream agents preserve through synthesis; structuring reports with explicit sections distinguishing well-established findings from contested ones, preserving original source characterizations and methodological context; completing analysis with conflicting values included and explicitly annotated, letting the coordinator decide reconciliation; requiring publication or data-collection dates in structured outputs; rendering different content types appropriately (financial data as tables, news as prose, technical findings as structured lists) rather than converting everything to one uniform format.
*Self-audit:* You can explain what to do with two credible-but-conflicting numbers, and why averaging them is wrong.

### Distilled notes
Synthesis across sources fails when **provenance dissolves in summarization**. If a subagent compresses "Source A (2026-01, [url]) reports 12%" down to "about 12%," the claim survives but its **source, excerpt, and date** are gone — and once gone, a downstream agent can't verify, weigh, or reconcile it. The fix is a **structured claim-source mapping** emitted by every subagent: each claim carries its source (URL or document name), the relevant **excerpt**, and its **publication or collection date**. The synthesis agent's job is to **preserve and merge** these mappings, not flatten them into anonymous prose.

**Conflicting statistics** are the signature test. When two credible sources give different numbers, **keep both, each with its attribution and date**. Do *not* **average** them — an average fabricates a figure that appears in no source and erases the fact that a disagreement exists. Do *not* **arbitrarily pick one** — that hides the conflict. Structure the report to separate **well-established findings from contested ones**, preserve each source's original characterization and methodological context, and let the coordinator decide how to reconcile before synthesis collapses it.

**Dates** carry more weight than they look. Requiring publication or collection dates prevents the **temporal-misinterpretation** trap: two figures from different periods aren't contradictory — they're a time series — and without dates a synthesis agent will read them as a conflict (or silently treat stale data as current). When sources are partial or unavailable, apply the **coverage annotations** from 5.3: synthesize what you have and explicitly flag what is well-supported versus where the gaps are — *absence of evidence is not a confirmed negative, and is not a license to fabricate.* Finally, render each content type in its natural form — **financial data as tables, news as prose, technical findings as structured lists** — instead of forcing everything into one uniform format that loses meaning.

### Deep-dive prompt
> I'm studying provenance and uncertainty in multi-source synthesis. (1) Explain how source attribution gets lost in summarization and design the structured claim-source mapping (source, excerpt, date) that subagents must emit and synthesis must preserve. (2) Give the correct handling of two credible sources with conflicting statistics, and explain precisely why averaging and arbitrary selection are both wrong. (3) Explain why publication/collection dates prevent temporal misinterpretation, and how coverage annotations handle partial sources without fabricating. (4) Quiz me: give me five short synthesis situations one at a time and ask "preserve, annotate, or reconcile — and how?", then critique my answers.

### Active-recall self-check
1. What three pieces must a claim-source mapping carry, and what breaks in synthesis if they're dropped during summarization?
2. Two credible sources report different numbers for the same metric. What do you do, and why are averaging and picking one both wrong?
3. Why require publication/collection dates in every structured output, and what error do they prevent?

## Decision heuristics recap

Five heuristics eliminate most wrong answers in this domain:

1. **Persist the facts; don't summarize them, and don't bury them.** Transactional facts — amounts, dates, IDs, statuses, customer-stated expectations — live in a persistent "case facts" block injected into every prompt, *outside* the summarized history. In a long input, put key findings at the beginning and the end (never in the middle) with section headers for the body. Summarization and position effects both destroy critical information silently — externalize and reposition it before they do.
2. **Sentiment and uncalibrated confidence are not signals.** Escalate on an explicit human request, a policy gap or silence, missing authority, or no progress — not on an angry tone or a self-reported confidence score, because neither correlates with whether the case is solvable. Acknowledge frustration and offer to resolve a simple in-scope request; ask for another identifier on an ambiguous match rather than guessing.
3. **Empty is not failure, and a hidden error is worse than a loud one.** Distinguish an access failure (retryable) from a valid empty result (do not retry); never report empty-as-success and never kill the whole workflow on one subagent's failure. Recover locally for transient faults and propagate only the unresolvable — with failure type, what was attempted, partial results, and alternatives — so the coordinator can decide.
4. **Preserve provenance; never average a conflict.** Carry each claim's source, excerpt, and date through synthesis instead of flattening it to anonymous prose. When credible sources disagree, keep both with attribution and dates and separate well-established from contested findings — averaging fabricates a number in no source, and picking one hides the conflict. Dates keep a time series from being misread as a contradiction.
5. **The aggregate hides the failure.** A high overall accuracy can mask a broken segment, so measure by document type and field with stratified sampling before automating, and route low-calibrated-confidence or contradictory-source cases to human review. Likewise, externalize findings to scratchpads and manifests and isolate verbose exploration in subagents, so a long session doesn't quietly degrade into "typical patterns."
